# WorkoutCrew 헌법

## 핵심 원칙

### I. 도메인 규칙의 권위
모든 구현은 `docs/domain-model.md`에 명시된 고유성, 길이 및 범위 제한, 소속 관계의
수, 크루 역할 등의 불변 조건을 반드시 보존해야 한다. 요청의 구조적 유효성 검사는
요청 경계에서 수행해야 하며, 저장된 데이터 조회와 유스케이스 조율이 필요한 검증은
서비스 계층에서 수행해야 한다. 상태에 의존하는 불변 조건은 도메인 모델과 필요한 경우
데이터베이스 제약 조건으로 보호해야 한다. 도메인 규칙을 변경할 때는 관련 문서와 테스트를
동일한 변경에서 함께 수정해야 한다. 이를 통해 컨트롤러, 서비스, 영속성 코드 사이에서
동작이 달라지는 문제를 방지한다.

### II. 계층 경계 준수
애플리케이션은 `user`, `auth`, `crew`, `global` 관심사로 구성된 단일 Spring Boot
애플리케이션 구조를 유지해야 한다. 각 도메인 내부의 의존성은 컨트롤러에서 서비스로,
서비스에서 도메인 또는 리포지토리로 흘러야 한다. 컨트롤러는 HTTP 변환, 요청 DTO의
구조적 검증, 서비스 호출만 담당해야 한다. 서비스는 유스케이스, 데이터 의존적 검증,
트랜잭션 경계를 조율해야 한다. 도메인 객체는 핵심 상태와 비즈니스 규칙을 소유하고,
리포지토리는 영속성 접근을 담당해야 한다. 컨트롤러가 리포지토리를 직접 호출하거나
컨트롤러에 영속성 책임을 두는 방식으로 이 경계를 우회해서는 안 된다.

### III. 일관된 API 응답 계약
모든 REST API 응답 본문은 최상위 필드로 `status`, `message`, `data`, `timestamp`만을
제공해야 한다. `status`에는 숫자형 HTTP 상태 코드를 담아야 하며 실제 HTTP 응답 상태와
반드시 일치해야 한다. `message`에는 처리 결과를 간결하게 설명하는 문구를 담아야 한다.
성공한 GET 요청의 `data`에는 요청한 응답 데이터를 담아야 한다. 성공한 POST, DELETE,
PATCH 응답의 `data`는 기본적으로 `null`이어야 하며, 클라이언트가 응답값을 사용해야 하는
요구사항이 엔드포인트 계약에 명시된 경우에만 null이 아닌 값을 허용한다. 오류 응답과
반환 데이터가 없는 응답의 `data`는 `null`이어야 한다.

`timestamp`에는 응답 생성 시각을 초 단위까지 기록해야 하며, 24시간제를 사용하는
`YYYY-MM-DDThh:mm:ss` 형식이어야 한다. 예시는 `2026-08-23T14:05:09`이다. 성공과 오류
처리 경로가 서로 다른 응답 구조를 사용하지 않도록 공통 응답 계약을 중앙에서 적용해야
한다. 각 HTTP 메서드와 대표 오류 응답에 대해 필드 존재 여부, HTTP 상태 일치 여부,
`data`의 null 허용 규칙, 타임스탬프 형식을 계약 테스트로 검증해야 한다.

### IV. 보안과 소속 관계의 무결성
사용자 비밀번호 원문은 저장하거나 로그에 기록해서는 안 되며, 승인된 단방향 비밀번호
해시를 적용해야 한다. 인증과 인가는 Spring Security를 사용해야 한다. 크루에 영향을 주는
작업은 상태를 변경하기 전에 사용자의 소속 여부와 필요한 `MEMBER` 또는 `MANAGER` 역할을
모두 검증해야 한다. 각 크루에는 관리자가 정확히 한 명 존재해야 하며, 관리자 위임,
크루원 추방, 크루 탈퇴, 크루 삭제는 이 불변 조건을 원자적으로 보존해야 한다. 비밀값,
자격 증명, 세션 정보, 민감한 개인정보는 응답 메시지나 로그에 포함해서는 안 된다.

### V. 관찰 가능한 동작의 테스트 증명
변경된 모든 유스케이스에는 성공 경로, 관련 유효성 경계값, 인가 실패, 도메인 불변 조건을
검증하는 자동화 테스트가 있어야 한다. JPA 동작이나 데이터베이스 제약 조건에 의존하는
리포지토리 동작은 통합 테스트로 검증해야 한다. REST 엔드포인트는 공통 응답 계약을
포함하여 HTTP 경계에서 테스트해야 한다. 테스트는 결정적이어야 하며 변경 사항을 병합하기
전에 모두 통과해야 한다. 운영 중 발견된 결함을 수정할 때는 회귀 테스트를 함께 추가해야
한다.

## 기술 및 API 제약 조건

- 실행 환경은 Spring Boot를 사용해야 하며, 영속성에는 Spring Data JPA, 운영
  데이터베이스에는 MySQL, 인증과 인가에는 Spring Security, 외부 API에는 REST를
  사용해야 한다.
- 공개 엔드포인트의 메서드, 경로, 요청 검증, 인가 규칙, HTTP 상태, 메시지, 응답 데이터
  구조를 문서화해야 한다.
- 여러 상태 변경을 포함하는 데이터베이스 쓰기는 모든 관련 불변 조건을 보존하거나 전체를
  롤백하는 하나의 트랜잭션 안에서 실행해야 한다.
- API 타임스탬프는 이 헌법의 응답 계약을 따라야 한다. 시간대 기준은 서비스 전체에서
  일관되어야 하며 클라이언트가 의존하기 전에 문서화해야 한다.
- MVP 범위는 `docs/requirements.md`와 일치해야 한다. 해당 범위를 벗어나는 기능은 별도의
  명시적 명세와 검토를 거쳐야 한다.
- 프로젝트에서 새로 만들거나 수정하는 모든 Markdown 문서는 원칙적으로 한글로 작성해야
  한다. 코드 식별자, 명령어, 파일 경로, 프로토콜 필드명, 고유한 기술 용어는 정확성을 위해
  원문 표기를 유지할 수 있다. 외부 원문을 인용하거나 외부 제출 형식이 다른 언어를 요구하는
  경우에는 그 범위에서만 예외를 허용하고 문서에 예외 사유를 명시해야 한다.

## 개발 절차 및 품질 기준

1. 모든 변경은 승인된 명세 또는 `docs/`에 기록된 요구사항에서 시작해야 한다.
2. 구현 전에 영향을 받는 도메인 불변 조건, 인가 규칙, API 계약, 트랜잭션 경계를
   식별해야 한다.
3. 가장 적절한 수준에 테스트를 추가하거나 수정해야 하며, 엔드포인트 변경 시에는 HTTP
   계약 테스트를 포함해야 한다.
4. 선언된 패키지와 계층 경계 안에서 구현해야 한다. 둘 이상의 도메인이 사용하는 공통
   횡단 관심사만 `global` 아래에 둘 수 있다.
5. 병합 전에 전체 자동화 테스트를 실행하고 스키마, 보안, API 호환성을 검토해야 한다.
6. 검토자는 헌법이 먼저 개정되지 않은 상태에서 MUST 성격의 의무 규칙을 위반한 변경을
   승인해서는 안 된다.

## 거버넌스

이 헌법은 WorkoutCrew의 최상위 엔지니어링 정책이다. 명세, 계획, 작업 목록, 문서,
구현은 모두 이 헌법을 준수해야 하며 서로 충돌할 경우 이 헌법이 우선한다.

개정안에는 변경 이유, 호환성 영향, 필요한 마이그레이션, 영향을 받는 산출물을 명시해야
한다. 개정에는 유지관리자의 명시적인 검토와 승인이 필요하다. 개정 내용과 직접 영향을
받는 모든 문서는 동일한 변경에서 함께 수정해야 한다.

버전은 유의적 버전 체계를 따른다. 거버넌스 규칙의 하위 호환되지 않는 삭제나 재정의에는
MAJOR, 새로운 원칙 또는 의무의 실질적인 확장에는 MINOR, 의무를 변경하지 않는 명확화에는
PATCH 버전을 적용한다. 제정일은 최초 채택일을 유지하고, 최종 개정일은 규범적 내용이
변경될 때마다 갱신한다.

모든 명세 및 계획 검토에는 헌법 준수 확인이 포함되어야 한다. 모든 Pull Request에는 관련
테스트 통과 근거가 있어야 하며 의도적으로 추가한 복잡성이나 계약 변경을 명시해야 한다.
프로젝트 아키텍처, 보안 요구사항, 공개 API 규칙이 실질적으로 변경되면 유지관리자는 이
헌법을 검토해야 한다.
