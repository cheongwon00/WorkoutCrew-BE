# WorkoutCrew MVP 데이터 모델

## 설계 원칙

- 기존 `docs/domain-model.md`의 `User`, `Crew`, `CrewUser`와 모든 필드를 유지한다.
- 새로운 비즈니스 엔티티를 추가하지 않는다.
- 입력 검증, 도메인 불변 조건, 데이터베이스 제약을 함께 사용한다.
- 비밀번호 원문은 입력 검증 직후 단방향 인코딩하며 영속 모델과 로그에 전달하지 않는다.
- 모든 관계 변경은 서비스 트랜잭션 안에서 수행한다.

## 1. 사용자(User)

WorkoutCrew 계정과 로그인 주체를 나타낸다.

| 필드 | 의미 | 필수 | 검증 및 저장 규칙 |
|------|------|------|-------------------|
| `id` | 사용자 식별자 | 예 | 양의 정수, 서버 생성, 변경 불가 |
| `email` | 로그인 이메일 | 예 | 올바른 이메일 형식, 전체 사용자에서 고유 |
| `password` | 단방향 인코딩된 비밀번호 | 예 | 입력 원문은 8~20자, 저장값은 인코더 전체 결과를 수용 |
| `nickname` | 공개 닉네임 | 예 | 2~10자, 전체 사용자에서 고유 |

### 데이터베이스 제약

- 테이블명: `users`
- 기본 키: `id`
- 고유 키: `email`, `nickname`
- `email`, `password`, `nickname`: NOT NULL
- 비밀번호 열은 알고리즘 식별자를 포함한 인코딩 결과를 수용할 수 있는 길이로 정의한다.

### 상태 전이

1. **회원가입**: 입력 검증 → 이메일·닉네임 중복 확인 → 비밀번호 인코딩 → 사용자 생성.
2. **닉네임 변경**: 본인 인증 → 길이 검증 → 자기 자신을 제외한 중복 확인 → 변경.
   현재 닉네임과 같은 요청은 변경 없는 성공으로 처리한다.
3. **회원탈퇴**: 사용자 잠금 → 관리 크루들을 ID 순으로 잠금·삭제 → 남은 일반 소속 관계
   삭제 → 사용자 삭제 → 커밋 후 모든 인증 세션 만료.

## 2. 크루(Crew)

사용자들이 함께 운동 활동을 수행하는 모임을 나타낸다.

| 필드 | 의미 | 필수 | 검증 및 저장 규칙 |
|------|------|------|-------------------|
| `id` | 크루 식별자 | 예 | 양의 정수, 서버 생성, 변경 불가 |
| `name` | 크루 이름 | 예 | 2~20자, 전체 크루에서 고유 |
| `password` | 가입용 비밀번호의 인코딩 값 | 예 | 입력 원문은 4~8자, 원문 저장·노출 금지 |
| `maxUsers` | 가입 가능한 최대 인원 | 예 | 2~100, 현재 크루원 수 이상 |
| `weeklyCertificationGoal` | 주간 운동 인증 목표 | 예 | 1~7회 |

### 데이터베이스 제약

- 테이블명: `crew`
- 기본 키: `id`
- 고유 키: `name`
- 모든 필드: NOT NULL
- CHECK: `max_users`는 2 이상 100 이하
- CHECK: `weekly_certification_goal`은 1 이상 7 이하
- 가입 비밀번호 열은 인코딩 결과 전체를 수용할 수 있는 길이로 정의한다.

### 상태 전이

1. **생성**: 속성 검증 → 이름 중복 확인 → 비밀번호 인코딩 → 크루 생성 → 생성자의
   `MANAGER` 소속 생성. 크루와 소속은 같은 트랜잭션에서 함께 성공하거나 함께 롤백한다.
2. **수정**: 관리자 확인 → 크루 쓰기 잠금 → 제공된 필드만 검증·변경. 최대 인원은 잠금 후
   계산한 현재 인원보다 작게 줄일 수 없다. 현재 값과 같은 요청은 변경 없는 성공이다.
3. **삭제**: 관리자 확인 → 크루 쓰기 잠금 → 크루 삭제. 모든 `CrewUser`는 외래 키 cascade로
   함께 삭제한다.
4. **관리자 탈퇴**: 일반 소속 삭제가 아니라 위의 크루 삭제 전이로 처리한다.

## 3. 크루 소속(CrewUser)

사용자와 크루의 다대다 소속 관계 및 크루 내 역할을 나타낸다.

| 필드 | 의미 | 필수 | 검증 및 저장 규칙 |
|------|------|------|-------------------|
| `id` | 소속 관계 식별자 | 예 | 양의 정수, 서버 생성, 변경 불가 |
| `user` | 소속 사용자 | 예 | 존재하는 `User` 참조 |
| `crew` | 소속 크루 | 예 | 존재하는 `Crew` 참조 |
| `role` | 크루 내 역할 | 예 | `MEMBER` 또는 `MANAGER` |

`manager_crew_id`는 `role`이 `MANAGER`일 때만 `crew_id` 값을 갖고 그 외에는 null인
데이터베이스 제약용 보조 열이다. 도메인 상태나 외부 응답 필드는 아니다. MySQL은
`ON DELETE CASCADE` 외래 키의 기준 열을 생성 열 식에 사용하는 구성을 허용하지 않으므로,
실제 스키마에서는 일반 nullable 열과 CHECK 제약으로 같은 조건을 강제하고 역할 전이
트랜잭션이 값을 함께 변경한다. 이 구현 차이는 `crew_id` 삭제 cascade와 조건부 관리자
고유성을 동시에 유지하기 위한 것이며 도메인 필드나 역할 규칙을 바꾸지 않는다.

### 데이터베이스 제약

- 테이블명: `crew_user`
- 기본 키: `id`
- 복합 고유 키: `(user_id, crew_id)`
- 조건부 고유 키: `manager_crew_id`
- CHECK: `role`은 `MEMBER` 또는 `MANAGER`
- CHECK: `MANAGER`이면 `manager_crew_id = crew_id`, `MEMBER`이면 `manager_crew_id IS NULL`
- `user_id`, `crew_id`, `role`: NOT NULL
- `crew_id` → `crew.id`: 삭제 시 cascade
- `user_id` → `users.id`: 삭제 제한. 회원탈퇴 서비스가 소속을 먼저 정리해야 하며 관리
  크루를 남긴 채 사용자를 직접 삭제하는 것을 방지한다.
- 조회 인덱스: `user_id`, `crew_id`, `(crew_id, role)`

### 불변 조건

- 동일한 사용자와 크루의 소속 관계는 최대 하나다.
- 각 크루에는 `MANAGER`가 정확히 한 명 존재한다.
- `MANAGER`와 `MEMBER`는 반드시 해당 크루에 소속된 사용자다.
- 전체 소속 수는 `Crew.maxUsers` 이하이다.

조건부 고유 키는 관리자가 둘 이상인 상태를 차단한다. 관리자가 최소 한 명인 상태는 크루
생성·위임·삭제 이외의 관리자 관계 제거를 금지하여 보장한다.

### 상태 전이

1. **일반 가입**: 크루 잠금 → 비밀번호 확인 → 중복 확인 → 현재 인원 확인 → `MEMBER`
   생성. 고유 키와 정원 검증 중 하나라도 실패하면 전체 롤백한다.
2. **일반 탈퇴**: 크루 잠금 → 본인의 `MEMBER` 관계 확인 → 해당 관계 삭제.
3. **추방**: 크루 잠금 → 요청자의 `MANAGER` 확인 → 대상의 `MEMBER` 확인 → 대상 관계 삭제.
4. **관리자 위임**: 크루 잠금 → 요청자와 대상 재검증 → 기존 관리자를 `MEMBER`로 변경하고
   flush → 대상을 `MANAGER`로 변경하고 flush → 관리자 수 검증 → 커밋.
5. **관리자 탈퇴**: 관계만 삭제하지 않고 크루와 모든 관계를 함께 삭제.

## 4. 관계

```text
User 1 ─── N CrewUser N ─── 1 Crew
```

- 한 사용자는 여러 크루에 가입할 수 있다.
- 한 크루에는 최대 `maxUsers`명의 사용자가 가입할 수 있다.
- `CrewUser`가 사용자와 크루 사이의 소속 및 역할을 표현한다.

## 5. 잠금 및 트랜잭션 규칙

| 유스케이스 | 잠금 시작점 | 원자적 변경 |
|------------|-------------|-------------|
| 크루 가입 | 대상 `Crew` 쓰기 잠금 | 정원 확인과 `CrewUser` 생성 |
| 최대 인원 수정 | 대상 `Crew` 쓰기 잠금 | 현재 인원 확인과 `Crew` 변경 |
| 일반 탈퇴·추방 | 대상 `Crew` 쓰기 잠금 | 권한·역할 확인과 관계 삭제 |
| 관리자 위임 | 대상 사용자와 `Crew` 쓰기 잠금 | 기존 관리자 강등과 대상 승격 |
| 크루 삭제 | 대상 `Crew` 쓰기 잠금 | 크루와 모든 소속 관계 삭제 |
| 회원탈퇴 | 대상 `User`, 관리 `Crew`를 ID 순으로 쓰기 잠금 | 관리 크루·일반 소속·사용자 삭제 |

여러 행을 잠글 때는 `User` ID → `Crew` ID → `CrewUser` ID의 오름차순을 따른다. 잠금 이후
권한과 현재 상태를 다시 검증한다. 런타임 도메인 예외와 데이터베이스 제약 위반은 전체
트랜잭션을 롤백한다.

## 6. 인증 세션 상태

인증 세션은 비즈니스 엔티티가 아니며 서버의 `HttpSession`과 `SessionRegistry`가 관리한다.

- 한 사용자는 여러 활성 세션을 가질 수 있다.
- 일반 로그아웃은 요청에 사용된 현재 세션만 무효화한다.
- 회원탈퇴가 커밋되면 해당 사용자의 모든 활성 세션을 완료 응답 전에 만료시킨다.
- 서버를 여러 인스턴스로 확장할 때는 공유 세션 저장소가 필요하지만 단일 인스턴스 MVP에는
  포함하지 않는다.

## 7. 외부 노출 규칙

- 사용자 비밀번호, 크루 비밀번호, 인코딩 값, 이메일은 크루 및 크루원 응답에 노출하지
  않는다.
- 크루 목록은 `id`, `name`, `maxUsers`, `currentUsers`, `weeklyCertificationGoal`만 제공한다.
- 크루원 목록은 `userId`, `nickname`, `role`만 제공한다.
- 엔티티 객체를 직접 직렬화하지 않고 계약에 정의된 조회 모델만 응답한다.
